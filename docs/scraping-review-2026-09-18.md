# v1.4.6.28 问题排查与 v1.4.6.29 修复

本文件按对话时间记录 2026-09-18 的排查、当时的拟议方案和用户批准后的本地实现。原文中的“待批准”“尚未修改”描述的是实施前状态；当前进度见文末“实施与验证”。本批目标是修复监控刮削失败，保持前端搜索结果规则。

## 已复现的事实

1. JavDB 实时搜索 `MXGS-713` 和 `HODV-20489` 均返回精确番号卡片，详情地址分别为 `/v/Rk69g`、`/v/a833R`。当前卡片使用 `a.box`；仓库的 `javdb._parse_list()` 只遍历 `div.item`。按实时结构制作的最小输入在现有解析器中返回 **0 条**。聚合搜索和自动刮削随后都收不到 JavDB 条目。
2. `HODV-20489` 的详情页把番号显示为 `<span class="value"><a>HODV</a>-20489</span>`。现有 `javdb._parse_detail()` 遇到链接时只拼接链接文字，解析结果为 **HODV**。`scrapers.enrich()` 的精确番号校验因此会拒绝该详情。
3. 该详情页封面 `https://c0.jdbstatic.com/covers/a8/a833R.jpg` 在浏览器实际加载为 **800×538**。现有详情封面选择器能取得此地址；问题发生在列表解析和详情身份校验之前。运行本机后端的直接 HTTP 测试在 18 秒内超时，因此尚不能声称本机完整网络刮削成功。
4. 搜索框的 `detect_search_mode()` 将 `MXGS 713` 和 `HODV 20489` 判为番号搜索，但监控文件的 `_code_from_name()` 当前只识别连字符形式；若实际文件名也使用空格，无法进入后续刮削。
5. JavDB 直接用空格检索 `MXGS 713` 时，精确的 `MXGS-713` 在当前第一页排第 8；前 3 条是其他番号。当前小范围来源查询会先截取前 3 条再做精确番号过滤，因此同类排序下也可能漏掉真实结果。

## 现有流程与触发条件

- 前台 `/api/search` 根据启用来源并发抓列表，番号模式在每个来源返回后再严格核对番号。JavDB 旧卡片选择器造成其结果为空；若别的来源也未命中，页面显示无结果。
- 直接放入监控目录的视频不要求来自下载器，但必须是支持的视频扩展名、达到设置的最小大小（默认 100 MB），且文件及所在批次连续稳定至少两次、静置至少 300 秒。已配置的下载器若离线，当前扫描会整体暂停，这是现有防误处理规则。
- 通过检查后，从文件名或父目录识别番号。未匹配推送元数据时，按 `JavBus → JavDB → DMM → AVSOX → AVMOO` 中已启用的来源依次精确搜索；JAV321 不参与自动刮削。
- 命中元数据后抓详情、校验封面图片字节，必要时先从已启用的 JavDB 寻找有效封面；NFO、poster、fanart 校验成功后才归档。失败保留源视频。
- 因此若 `HODV-20489` 仅在 JavDB 可用，必须启用 JavDB，且本机到 JavDB、图片 CDN（或配置的代理、FlareSolverr）可达。目前解析器缺陷会让该路径失败，即使网页和封面本身可访问。

## 拟议改动，需用户批准后执行

1. **适配 JavDB 列表卡片**：仅在 JavDB 解析器中同时支持旧 `div.item` 和新 `a.box[href*="/v/"]`；保留 `/v/` 地址约束、番号字段及现有封面候选逻辑。以精确番号过滤结果，避免把相似番号误收为命中。页面结构变化不得改变 JavBus 等来源。
2. **修复详情番号读取**：对“番号”字段读取 `span.value` 的完整可见文本，包括链接之后的 `-20489`；其他多链接字段维持原处理。继续使用 `enrich()` 的严格番号校验，避免错片和错封面。
3. **补足人工文件名格式**：在既有正则中接受字母前缀与数字之间的单个空格（如 `MXGS 713.mp4`），标准化为 `MXGS-713`；保留边界和数字位数限制，不扩大纯数字、广告前缀或分集识别。若用户确认实际文件名始终含连字符，此项可取消。
4. **防止先截断再精确过滤**：番号模式的单来源查询应检查完整当前页的卡片，再精确匹配并施加 3 条等结果上限；最多仍维持现有页数与超时，避免大范围爬取。关键词、演员搜索的上限策略不变。
5. **回归验证**：增加旧、新 JavDB 卡片及拆分番号详情的 HTML 测试；验证 `MXGS-713`、`MXGS 713`、`HODV-20489` 的前台精确检索、人工文件名识别、已启用 JavDB 时的封面来源顺序和有效图片字节。以临时监控与归档目录模拟完整流程，分别覆盖正常封面、JavDB 唯一封面、网络超时和失败保源。在可连通的运行环境再实抓两个番号，确认 NFO、poster、fanart 与任务状态。不会用真实视频或用户媒体库进行破坏性测试。

## 暂不建议改变的规则

现有严格番号校验、JAV321 不参加普通搜索与自动刮削、失败不归档以及下载器离线时暂停扫描，均有防错目的。这些规则本轮不拟修改。若希望下载器离线时也处理手动文件，需要另行设计能可靠区分手动文件与未完成下载的机制。

## 2026-09-18 补充：HODV/BNDV 批量失败截图

截图列出的 12 个文件名均能被当前 `_code_from_name()` 识别；例如 `HODV20516.avi → HODV-20516`、`HODV-20480-U.mp4 → HODV-20480`、`BNDV-702.wmv → BNDV-702`。任务记录显示“未找到影片信息”，说明这些任务已越过文件名识别阶段，失败发生在来源检索或精确匹配阶段。该提示把站点不可达和没有匹配合并显示，单靠截图不能判断用户代理是否同时故障。

JavDB 当前网页对截图中的 8 个 HODV 编号均返回精确卡片；`BNDV-00702` 也能精确命中。JavBus 实测 `HODV-20516` 和 `BNDV-00702` 的站内搜索无结果，因此 JavDB 对这些项目尤其重要。即使网络正常，现有 JavDB `div.item` 解析器面对实际 `a.box` 页面仍返回零条，可独立造成批量失败。

`BNDV-633`、`BNDV-560`、`BNDV-702` 的当前写法在 JavDB 搜索没有精确结果；JavDB 分别能找到 `BNDV-00633`、`BNDV-00560`、`BNDV-00702`。仅凭文件名不能证明短号与补零号是同一作品。代码的 `_exact_code_rows()` 与 `_source_item_for_code()` 会拒绝这两种写法之间的匹配，这是另一项独立原因。截图同时含 `BNDV-702.wmv` 和 `BNDV-00702.wmv`，不能直接将两份文件无条件规范成同一个归档番号，否则可能误合并文件。

现有“测试 JavDB 连通”把 `reachable` 定义为 `bool(_parse_list(html))`。用 HTTP 200、无请求错误、含新 `a.box` 卡片的页面模拟，诊断仍返回 `reachable=false`、`item_count=0`。因此旧版测试面板显示“无法获取片源”不能单独证明代理故障；需同时查看 HTTP 状态、请求错误、Cloudflare 标记和返回页面类型。

### 需另行批准的 BNDV 补零方案

在完成上述 JavDB 列表与详情修复后，只对 `BNDV-` 加三位数字且原编号精确检索无结果的场景，尝试一次五位数字候选（`BNDV-633 → BNDV-00633`），但先作为待确认别名展示，不自动写入该候选的 NFO/封面或归档。用户确认文件确属该作品后才以五位番号刮削，任务记录同时保留原始文件名、原识别番号和确认后的番号。若监控目录里同时存在短号与五位号，或归档目标已存在，禁止自动合并或覆盖，分别保留源文件并给出冲突提示。增加短号、长号并存、错号拒绝、目录冲突、失败保源测试。此方案会改变刮削匹配与归档判定，未获批准前不实施。

### 需批准的诊断口径修复

将“HTTP 页面可达且不是盾/登录/年龄页”与“影片卡片解析成功”分开记录；诊断接口保留 `http_status`、`error` 等字段，新增或明确区分页面可达、解析条数与解析失败的状态。在来源诊断和刮削任务中分别提示页面结构变化、超时、代理错误、Cloudflare 或地区限制，不改变普通搜索结果规则。用 HTTP 200 新卡片、超时、验证页三类输入回归，避免把解析器缺陷误报为用户代理问题。

## 用户澄清后的目标：修复“前端搜得到、监控刮削失败”（待批准实施）

前端搜索目前大多正常，本批不修改前端搜索结果的筛选或展示规则，也不让批量监控依赖用户先在前端搜索。验收条件是：文件名识别为番号后，若已启用来源的前端搜索能找到该番号的作品，监控独立搜索应能找到同一作品；在该作品有有效封面或其他已启用来源可补图时，刮削应完成 NFO、poster、fanart。若网络或图片不可用，应给出具体失败阶段，而非一律显示“未找到影片信息”。

### 已复现的前端/监控分叉

1. **取样截断**：前端 `scrapers.search()` 通常按配置最多请求 300 条；监控 `_scrape_one()` 对每个来源只请求前 5 条，封面回查只请求前 3 条。以同一来源返回前 7 条相似作品、第 8 条才是精确 `MXGS-713` 的模拟数据测试：前端能显示目标，监控返回“未找到影片信息”。应让监控在既有页数/超时界限内先检查完整页是否有精确编号，再限制返回数量；不接受相似番号的第一条。
2. **前端可回退缩略图，监控漏试**：前端 `coverCandidateUrls()` 会依次尝试 `cover`、`cover_thumb` 和各来源候选；未合并的监控列表条目在 `_ensure_downloadable_cover()` 中只尝试 `cover`，重新搜同一来源时也只尝试 `cover`。以高清地址失败、缩略图字节有效的模拟测试：前端条目携带可用缩略图，监控从未请求该缩略图，最后报 `poster/fanart 未创建`。应在同一已确认番号的条目内优先尝试高清封面，失败后尝试其缩略图，再查详情和其他已启用来源；每个候选都校验真实图片字节。
3. **部分 JavDB 页面结构/详情不兼容**：新版 `a.box` 卡片解析为零条；HODV-20489 详情拆分的番号解析成 `HODV`，因身份校验失败而丢失详情。此项会在对应页面结构下同时影响前端和监控，不能据此推断用户当前所有前端命中记录都经过该页面结构。需兼容新旧结构并保留严格详情身份校验。
4. **失败后不自动重试**：周期监控无论成功失败都把文件放入进程内 `_processed`，同一进程后续扫描跳过；只有显式“立即扫描”清空该集合或重启后才重新尝试。因此一次临时超时、代理波动或 CDN 失败可使任务长期停留在失败。应对可恢复的网络/封面失败设计有限次延迟重试，仍保留源文件、不覆盖已归档作品；永久的番号不匹配不应无休止重试。

### 拟议实施顺序和验证

1. 先修监控的精确番号查找范围与封面候选顺序，前端搜索保持现状；同时给任务记录加上来源请求状态、卡片数、精确项是否命中、详情身份结果、各封面候选失败原因，不记录代理凭据。
2. 修 JavDB 新旧卡片兼容和详情番号的完整文本读取，以 `MXGS-713`、`HODV-20489` 验证；不改变 JavBus 等来源的身份匹配规则。
3. 对临时网络/图片失败增加有上限的重试与退避：初次失败后分别至少等待 5、15、30 分钟，最多额外尝试 3 次；在任务记录中持久化失败类别、已尝试次数和下次时间，重启后沿用。仅对超时、连接失败、盾/限流和图片下载失败重试；明确无精确番号、详情身份不符、文件冲突不自动重试。成功后清除重试状态，失败期间源视频保持原位。对 BNDV 短号/补零号继续保持严格匹配，另按上面的待确认方案处理，避免错片。
4. 使用临时监控目录验证：前端可见但精确项排第 8、高清坏而缩略图可用、详情番号拆分、JavDB 唯一封面、短暂网络失败后恢复、失败保源及成功归档；之后在网络可连通环境做真实来源与图片 CDN 端到端检查。测试中不用用户真实媒体库。
